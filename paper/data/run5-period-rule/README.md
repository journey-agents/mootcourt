Run 5 (the period rule, 4 Nov 2026): the folder of run 4 with the files that the period rule of P1 (docs/method.md call 199) and the corrections of the review of chunk N2 changed. Run 4 is kept in `paper/data/run4-review-l-fixes`; the run 4 reports of the data root are in `archive-pre-o/reports` and `archive-pre-o/models`.

What the rule changed: P1 takes its period level from the last complete quarter, and a quarter whose end is after the fit's data end sets no level. At the quarterly origins of the backtests the data end is the origin, so the three main backtests were rerun and every score, interval, coverage, gate verdict, decision value and table is identical to run 4 (`diff` of the JSON apart from the header model id and the values listed below). Fits at other dates change: the bundles (hence the model ids), and the synthetic guard diagnostics.

Changed (copied from the rerun or the corrected reports of the data root):
- `backtest-upworthy`, `backtest-asos`, `backtest-synthetic`: rerun. The scores are identical. Differences: `header.model_id` (a new bundle); in the Upworthy report the P0 rows of `p_sig_mean` (the planned-event table now reports the planned base rate P0 forecast, the correction of review N finding 9, which run 4 predated).
- `ablations/backtest-*` (45 files) and the ASOS main report: the `resolution_*` values of the multi-metric blocks (`tables.by_metric[].aggregate`) and `p_sig_mean` of P0, recomputed from the stored score tables by `scripts/refresh_discrimination.py` (run 4 had refreshed only `tables.aggregate`; the ASOS `by_metric` blocks still held the spread of the forecast under the name resolution, which is the finding that this refresh closes). The ablations themselves were not rerun: they fit at quarterly origins and the period rule changes nothing there.
- `card-latency.json`: rerun on the new bundle. Differences: `model_id`, `bundle_load_ms`, and the max, p50 and p95 of the four timing blocks (`cli_fresh_process_ms`, `in_process_ms`, `in_process_lambda_0.5_ms`, `service_ms`): all timings, none a count or a result. No table of `build_tables.py` reads this file.
- `paper-extras-synthetic`: rerun with the new rule. New or changed keys: `guard_period_control` (the control arm; the no-period arm records 0 rows in the period level, rerun alone with `--period-control-only` after review N3 and unchanged in every other value), `guard_held_out_gain` (the best candidate's held-out gain, clustered standard errors; the count `cells_skipped_without_held_out_rows` that the current code writes is absent from these rows, which predate it, and no published size has such a cell), and every value of `positive_control_sensitivity`, `guard_gain_diagnostic`, `guard_fit_fraction_stability` at 3,700 and 11,100 tests. `guard_admission_rates` is identical to run 4 in every value. `top_m_tail_share` differs in its timings and in 15 `share_p2_weight` values by up to 5e-5 (its bundle is fit with the default data end, so the period rule applies); no table of `build_tables.py` reads it, so no table digit moves.

Byte-identical copies of run 4 (not rerun, with the reason):
- `replay-upworthy`, `replay-asos`: rerun with the new rule and identical (zero differences outside timestamps), so the run 4 files stand.
- `learning-curve-upworthy`, `learning-curve-asos`, `ablations/backtest-upworthy--effect-scale-relative+s-star-realized`, `ablations/p2-guard-*`, `positive-control/*`, `paper-extras-upworthy`, `paper-extras-asos`: they fit at quarterly origins or read the main scores, which are unchanged.
- `gates.json`: a simulation, independent of P1. `run-log.json` and `scale/`: wall-clock measurements of run 4; the rule does not change their structure and they were not repeated.
