## Summary (five sentences, in the reviewer's own words, of what the paper claims and shows)

The package reads an archive of concluded A/B tests as a ledger of aggregates, forecasts for a proposed test the probability that it ends significant and positive together with an interval for the true effect, declines to rule when the ledger has no standing, and scores every forecast out of time with a rolling-origin backtest whose verdicts are gated by a power simulation. The README's headline block, which `scripts/verify_readme_numbers.py --reports paper/data/run5-period-rule` re-derives (3177 numbers checked, 0 mismatches), states a Brier skill against the base rate on the Upworthy archive of 0.0015 (-0.0018 to 0.0048) for P1 and 0.0015 (-0.0017 to 0.0047) for P2, neither distinguishable from the constant base rate, and on the ASOS archive -0.1073 (-0.2366 to -0.0020), worse than the base rate, with 4 of 4 cells undecidable at this n. What a practitioner receives is therefore the protocol and the tooling rather than a forecaster that wins: a vendor-neutral ledger format with admission as a status, a backtest report with gates and bootstrap intervals, frozen cards with a join key, a weekly join that types hits and misses, a one-page report card that can be published without the ledger, and an HTTP and MCP service. I followed the README and all six tutorials from a clean clone with no other context; every command of tutorials 1, 2, 4, 5 and 6 ran, and every printed output matched the page to the character, card ids, model ids and join counts included. The install step failed twice on a clone kept on the external exFAT drive that the README itself recommends for the data root (the venv path at `moot backtest`, the uv path at `uv sync`), and the README's `uv run moot` instruction fails outside the clone, so my major findings are onboarding defects that a newcomer hits before the first card, not defects of the experiments.

## Findings

- [major] README "Quickstart", install block, and docs/tutorials/01-first-card.md section 1; docs/troubleshooting.md "Working from a clone on an exFAT volume". The README's primary install path (`python3 -m venv .venv && source .venv/bin/activate` then `pip install -e .`, run in the root of the clone as the page says) succeeds on a clone kept on an exFAT drive, and so do `moot init`, `moot ingest` and `moot fit`; then `moot backtest --source sample` exits 2 with `Cannot decode configuration file PosixPath('.../.venv/lib/python3.11/site-packages/matplotlib/mpl-data/stylelib/.__classic_test_patch.mplstyle') as utf-8. error: 'utf-8' codec can't decode byte 0xb0 in position 37`, because the plotting library globs the `._` sidecar that macOS writes next to every file in the environment (19,356 such files under `.venv` after the install). `moot doctor` run from that same environment reports `OK` for every package and the ledger and model, so the health check the troubleshooting page says to start with does not see the condition. The troubleshooting page covers the uv path and the test suite but not this path, and the error text names a style file of the plotting library, not the drive, so a newcomer has nothing to search for. What would fix it: a sentence at the README install step and in tutorial 1 ("keep the environment on the internal disk; an environment on an exFAT drive breaks `moot backtest`"), a troubleshooting entry with this exact error text, and either a `moot doctor` line that fails when a `._` file is found under site-packages or a guard around the report's figure writing that prints one line naming the page instead of the traceback.
- [major] README "Quickstart", install block, and docs/troubleshooting.md "Keep the uv virtualenv on the internal disk". `uv sync --all-extras` in a clone on the exFAT drive exits 2 with `error: Failed to install: ruff-0.17.3-py3-none-macosx_11_0_arm64.whl ... RECORD file doesn't match wheel contents: Could not find entry for ruff-0.17.3.data/scripts/._ruff` after 13 s, and it first uninstalls two packages from an existing `.venv`, so a user who tried the pip path first is left with a damaged environment. The troubleshooting page documents the remedy (`UV_PROJECT_ENVIRONMENT` on the internal disk; with it the sync completed and the whole walkthrough ran), but it quotes a different error (`failed to copy ... ._ttx.1`) so a search for the actual message does not find the page, and the README install step does not point to it. What would fix it: the README install block should say in one line where the environment must live and link the troubleshooting entry; the entry should quote both error texts; `uv sync --extra dev` on the page should match the `--all-extras` the Makefile and CI use, or say they differ.
- [major] README "Quickstart" ("`uv sync` works too, and then `uv run moot ...` replaces `moot ...`", followed by "Leave the clone (`cd ..`) and make a project folder next to it") and docs/tutorials/01-first-card.md section 1 ("With `uv`, `uv sync` does the same and `uv run moot ...` replaces `moot ...` below"). From the project folder the page tells you to create, `uv run moot --version` fails with `error: Failed to spawn: moot. Caused by: No such file or directory (os error 2)`, because uv looks for a project in the current folder and its parents and finds none. Every later `uv run moot ...` in the quickstart fails the same way, so the uv path never reaches `moot init`. What would fix it: say `uv run --project ../mootcourt moot ...`, or tell the uv user to activate the environment (`source ../mootcourt/.venv/bin/activate`, or the `UV_PROJECT_ENVIRONMENT` path) and then call `moot` directly; the docs test should run one block through uv from outside the clone.
- [minor] README "Quickstart" timings and docs/tutorials/01-first-card.md sections 2 and 4. With the data root on the exFAT drive that the README recommends ("for example to an external volume (exFAT is fine) for large runs"), `moot init` took 90 s with no progress line (tutorial 1 says "about 20 seconds ... can take a minute") and `moot backtest --source sample` took 97 s of wall time against "about 10 seconds" (its own last line says `scored 330 rows over 11 origins in 11.3 s (report writing 5.2 s)`, so about 80 s are unaccounted for). The same two commands on the internal disk took 24 s and 12 s, so the printed timings hold there and the drive is the cause. What would fix it: one sentence saying that a data root on an exFAT volume is several times slower for the sample-sized commands, a progress line from `moot init` while it simulates the gates, and the backtest's timing line should cover its whole run.
- [minor] docs/troubleshooting.md "Working from a clone on an exFAT volume". Two more things a newcomer meets on such a clone are not on the page: `git status` in the fresh clone prints `error: non-monotonic index .git/objects/pack/._pack-....idx` twice, and `pip install -e .` prints about ten lines of `WARNING: Ignoring invalid distribution -httpx2 ...` (pip reads each `._NAME` sidecar as a package named `-NAME`). Both are harmless and both are cured by the page's `find . -name '._*' -type f -delete`, which should say so and should include `.git` in its scope. What would fix it: two lines on the page.
- [minor] docs/faq.md "How many tests do I need?", docs/tutorials/06-simulation-agent.md section 5, docs/tutorials/02-your-own-archive.md "How many experiments?". The gate sizes are stated differently on every page: the FAQ says "of the order of 175 and 400 at the release gate"; tutorial 6's printed output says `below the gate of 150 tests` while its prose two lines later says "49 judged experiments is far below the gate of 400"; tutorial 2 says "somewhere between 75 and 400"; the quick gates that `moot init` writes are 75 and 150 (report JSON `header.gate_by_base_rate` = `{"0.30": {"n_200": 75, "n_400": 150}}`), and the response letter's claims table says 175 and 250 tests at base rate 0.09. What would fix it: one sentence, repeated verbatim on the three pages, that the gate is a number of tests that depends on the base rate, with the three simulated rates and their sizes, and the stale "400" removed from tutorial 6's prose.
- [minor] docs/tutorials/02-your-own-archive.md step 6 ("Run `moot simulate gate-power --base-rate R` ... to size the gates by experiment at your own rate; it takes a few minutes") and `moot simulate gate-power --help`. Run as the page says with the report card's base rate (0.203), the command took 751 s (with two other jobs on the machine) and wrote `gates.json` with `rows_per_test` 5.0 and `icc` 0.67: by the help text these defaults are "the measured value of each base rate" of the two public archives, so a user's gates are sized with the within-test dependence of a public archive nearest their rate, not of their own ledger (the sample ledger has 3 rows per test), and the page does not say so nor tell the user to pass `--rows-per-test` and `--icc`. The result also differs from the quick gates by more than a factor of two (175 and 325 tests at power 0.90 against 75 and 150), so the "decidable" verdicts of the first report a newcomer reads flip once the advice is followed. What would fix it: the page should say that the two dependence settings default to a public archive's values and show where to read the ledger's own (the backtest report's `icc` and the header's rows per test), or the command should measure them from the source's ledger when `--source` is given; the timing should say ten to fifteen minutes.
- [minor] Card output, "Skill at this n" section (tutorials 1 and 2; `moot card` on any cell). The gate line reads `the gate needs 150 tests for a skill of 0.10 and 75 for 0.20 at base rate 0.30` while the Evidence section of the same card says `Base rate of significant positive results in the cell (P0): 0.117` (tutorial 2, `revenue_per_user`) or `0.275` (tutorial 1). A reader cannot tell that 0.30 is the gates file's simulated rate nearest the cell's and not a second measurement of the cell. What would fix it: "at the nearest simulated base rate, 0.30" on the card, and the same words in reference/card.md.
- [minor] Card output, "Request" line, and the frozen card JSON (`cards/1705a34c4ed02a00.json` in the quickstart). A card for a ledger with no text features (every cell of the sample, and any product-metric archive, which is the reader the README addresses) prints `Request: headline "", image changed: no, exposures per arm: 20000, ...`, and the JSON stores `"headline_changed": true` with `"headline": ""` and `"reference_headline": ""`. A data scientist with checkout and revenue metrics is told the card is about a headline and an image. What would fix it: omit the text fields from the rendered Request line when the ledger has no text columns (or print "text features: none in this ledger"), and store `headline_changed` as null or false when no headline was given.
- [minor] Backtest report, first table "Rows, tests, gates and abstention" (`reports/backtest-sample-*.md`, and README "Quickstart" which tells the reader to ignore two of its columns). Of the table's thirteen columns, `decidable_by_tests_base_0.3` repeats `decidable_by_tests` on every row, and `decidable` and `decidable_research` read `not computed: the gates count tests` on every row. A first-time reader is told in the README to skip columns of the first table they open. What would fix it: drop the two "not computed" columns when the gates count tests, and show the base-0.3 column only when it differs from the nearest-rate verdict.
- [minor] Report card (`reports/benchmark/ledger-<snapshot>.md`, tutorial 2 step 7), section "Gates". - [minor] docs/tutorials/01-first-card.md section 5 ("How to read the card") and docs/concepts.md glossary. The card line `P(true effect above 0): 0.585` is not explained in the line-by-line reading, and the glossary has no entry for it; the only definition is `p_win` in reference/card.md. ## Questions for the authors

1. Is a `moot reliability --source NAME` command planned, so that the weekly operator does not need the Python snippet of tutorial 4?
2. Could the card's request block be conditional on the ledger's feature columns, so that a ledger without text never shows headline fields, and `headline_changed` is not stored as true for an empty headline?
3. Where do the extra 80 s of `moot backtest` go when the data root is on an exFAT volume (97 s wall against the 11.3 s plus 5.2 s the command reports)? If it is the figure files and the many small report files, could the writer batch them, and should the README's "exFAT is fine" carry a timing caveat?
4. Could `moot doctor` detect an environment poisoned by `._` sidecars (a `._*.mplstyle` under site-packages is a sufficient test), given that the troubleshooting page tells the user to start with doctor and doctor says OK in that state?
5. The quick gates from `moot init` (75 and 150 tests at base rate 0.30) and the gates the paper uses (175 and 250 at 0.09) differ by more than a factor of two; should the sample ledger's base rate be set near the archives' so that the first report card a newcomer reads shows gates of the size the paper argues from?

## What is good (so it is not removed in revision)

- The tutorials are executable documents, and they are true: every printed output of tutorials 1, 2, 4, 5 and 6 matched my run to the character (card `1705a34c4ed02a00`, model `6e5029e03c73`, card `d56fd0ceb1e8cf08`, the twelve card ids of tutorial 4 and its join counts 3, 3, 4, 2, 0, 0, the HTTP 404 and 422 bodies, the MCP tool list and precedent weights). `tests/test_docs_run.py` is the mechanism, and it should stay.
- The reading order the pages teach (abstention first, then the probability against the base rate, then the interval, then the skill line) is the right one, and the card's "Skill at this n" section carries its own record with intervals and a gate verdict: a newcomer can see at once that `0.093 (90 percent interval -0.227 to 0.221, by test), measured on 7 rows from 7 tests` is no evidence. The card JSON's `skill.backtest` block (`brier_skill` 0.019536612428702083, interval -0.007325721361582272 to 0.0461606263369586, `n_tests` 110) agrees with the backtest JSON's `tables.aggregate` row for ALL/P2, so the card and the report cannot drift apart.
- Admission as a status and never a filter, the `--dry-run` preview, `moot ledger check`, and the ingest summary that counts admitted rows by cell: these answer the first questions a data scientist asks of any importer, and the mapping file of tutorial 2 (columns, constants, options with the interval level and the scale) is a model of how to bring a vendor export in without writing code.
- The one-page report card (tutorial 2 step 7) is readable without the paper and carries no experiment or cell name (0 matches for any of the three cell names or an experiment id in the file), so the FAQ's promise that it can be published without the ledger holds.
- Error paths are one line and name the cure: `moot card` without `--cell` lists the cells; `POST /card` for an unknown source returns a 404 that lists the known sources; the service refuses non-loopback Host headers; `moot backtest` on a too-small ledger names the minimum.
- The troubleshooting page's two tables (what doctor reports, why a card abstains) and the concepts page's flow diagram and glossary are the pages a newcomer actually needs, and they are complete for everything that happened to me except the install path.
- The README's "What the results show, and what the project does not show" list is unusually honest for an entry page, and the headline numbers in it are machine-checked against the report JSON.
- Code: `ruff check src tests scripts` passes; 1184 tests collect; the CLI maps the package's own error types to one-line messages with exit code 2; the service binds to loopback by default and loads models only from local artifacts checked by digest.
