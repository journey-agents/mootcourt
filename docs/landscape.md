# Landscape: technologies and research lines relevant to pre-launch prediction of experiment outcomes

Scope: every product, library, internal platform, AI tool and research line found that bears on predicting the outcome of an online controlled experiment before it runs, from a ledger of past experiments. Written so that an open-source package with a ledger, a predictor ladder (P0 base rate, P1 empirical-Bayes prior, P2 weighted precedents, P3 frozen human forecast, a stacked second opinion from pluggable simulation agents at earned weight), calibrated abstention, a rolling-origin backtest with gates, and a decision-value metric can position itself and import the ledgers organizations already keep.

Method: every claim was located with a web search and then fetch-verified against the vendor's own documentation, the paper, or the repository on 2 November 2026. The fetched URL follows each claim as "Fetched:". Where a page carried a date, it is recorded as "(page dated ...)". Items that could not be fetched after two attempts are marked UNVERIFIED and carry no details beyond what the search index showed. A second pass on 3 November 2026 verified leads from an independent research assistant's partial report; the items it added follow the same convention, and where a page could be read only through a reader proxy, a mirror copy or a documentation repository's source file, the "Fetched:" line says so. A third pass on 3 November 2026 verified the remainder of that report under the same conventions. "Not documented publicly" means the fetched vendor documentation does not describe the item. Research already covered in paper/related-work.md is referenced by its number there (for example RW 1.3) and is not re-summarized.

Conventions: "pre-launch outcome prediction" means a probability or distribution for a proposed experiment's result issued before any exposure data exists. "Experiment memory" means a searchable store of concluded experiments with decisions and learnings. "Learned prior" means a prior fitted from the organization's own past experiments rather than typed in by hand.

## 1. Commercial experimentation platforms

### 1.1 Statsig

- Statistics engine: frequentist by default with optional Bayesian analysis; sequential testing is a frequentist-only toggle; Bonferroni and Benjamini-Hochberg corrections; CUPED and a multi-covariate regression adjustment called CURE; stratified sampling; winsorization. The analysis type cannot be changed once an experiment starts. Fetched: https://docs.statsig.com/statsig-warehouse-native/features/experiment-options (page dated 2025-09-18) and https://docs.statsig.com/statsig-warehouse-native/features/statistics (page dated 2025-09-18). A third analysis type, SPRT, reads at any time and can accept the null; it "requires a baseline mean, standard deviation, and minimum detectable effect (MDE) for each metric", taken from the experiment's own control group (recommended) or entered by hand, where the manual values can be filled "from a previous experiment". Fetched: https://docs.statsig.com/experiments/advanced-setup/sprt.
- Historical priors: Bayesian mode defaults to a flat N(0, infinity) prior. "Use Informative Priors" lets the experiment team type a prior mean and standard error, and the docs recommend deriving them from "the average treatment effect of past experiments with a similar setup and population" and the standard deviation or average standard error of those effects. The derivation is manual; nothing fits the prior from the ledger. Fetched: https://docs.statsig.com/experiments/advanced-setup/bayesian.
- Experiment memory: a Knowledge Base with free-text search across teams, plus meta-analysis views (experiment timeline with ship decisions, metric correlations, "batting average" of how often a metric moves 1% or 10%). Described as descriptive; no priors or predictions are derived from it. Fetched: https://statsig.com/blog/experimental-meta-analysis-and-knowledge-base (post dated 9 October 2024). The Metric Impacts view filters to shipped experiments and buckets how often a metric moved by 1% or 10%, with the stated use "Check whether a claim that the next experiment moves this metric by 15% is realistic": a manual calibration check against the ledger, not a forecast. Fetched: https://docs.statsig.com/experiments/exploring-results/meta-analysis (page dated 2025-09-18). An "Experiment search" in natural language (beta, Warehouse Native only) returns three matching past experiments. Fetched: https://statsig.com/blog/statsig-ai-features (post dated 21 January 2026).
- Pre-launch power: a Power Analysis Calculator that uses historical metric mean and variance from a chosen population; one population type is "Previous Experiment" ("Use a prior experiment with a similar audience"). Output is MDE by week and a scenario matrix; analyses can be attached to an experiment. Fetched: https://docs.statsig.com/experiments-plus/power-analysis.
- AI features: AI Experiment Summary (purpose, ship recommendation, key metric observations) runs on collected data, after the fact. Fetched: https://statsig.com/updates/update/ai_experiment_summary (dated 19 December 2025). A hypothesis advisor critiques wording during setup; none of the listed features predicts outcomes before launch or uses past experiments as priors. Fetched: https://statsig.com/blog/statsig-ai-features.
- Export: CSV download (summary, exposures, raw data), Console API, CDP integrations, webhook, and a daily warehouse export. The export page lists no fields. Fetched: https://docs.statsig.com/integrations/data-exports/experiment_result_exports. The Warehouse Native results view `statsig_daily_results` does list fields: `experimentName`, `controlGroupName`, `testGroupName`, `metricName`, `metricType`, `controlMean`, `testMean`, `absoluteDelta`, `relativeDelta`, `absoluteDeltaCI`, `relativeDeltaCI`, `absoluteDeltaPValue`, `sequentialTestingAbsoluteDeltaPValue`, `controlUnits`, `testUnits`, `experimentStartTs`, `experimentEndTs`, `useCUPED`, `useSequential`, `ds`. The full view has 42 columns and also carries `experimentTeam`, `experimentTags`, `targetExposures`, `targetDuration`, `actualDuration`, `higherIsBetter`, `controlTotal`, `testTotal` and topline and projected-topline estimates with intervals (page dated 2025-09-18). There is no experiment id column and no decision column in the view. Fetched: https://docs.statsig.com/experiments/interpreting-results/access-whn. The Console API experiments list endpoint returns configuration, lifecycle dates (`startTime`, `endTime`, `decisionTime`) and the decision itself: `status` takes the values setup, active, decision_made, abandoned, archived, experiment_stopped and assignment_stopped, alongside `decisionReason`, `launchedGroupID`, `shipWithHoldout` and `wasAutoDisabled`; it returns no result fields, and Pulse result endpoints are referred to but not documented on that page. Fetched: https://docs.statsig.com/console-api/experiments. An importer can join the view to the Console API on experiment name to recover the shipped group.
- Gap: everything is post-exposure. The informative prior is the closest feature and it is typed by hand from eyeballed history; no outcome distribution, win probability or abstention exists before launch.

### 1.2 Optimizely (Web and Feature Experimentation)

- Statistics engine: Stats Engine sequential testing with false discovery rate control, so results "are always valid"; frequentist fixed-horizon and Bayesian modes are offered in beta via the customer success manager. CUPED, Stats Accelerator and a sample size calculator are not described on the methods overview page. Fetched: https://docs.optimizely.com/experimentation-strategy/docs/statistical-analysis-methods-overview (page dated 2026-08-05).
- Historical priors: not documented publicly. The sample-size guidance says the baseline conversion rate can be taken from analytics or from "a previous Optimizely Experimentation experiment", or from a monitoring campaign with no variations; history supplies the baseline, not an effect prior. Fetched: https://docs.optimizely.com/experimentation-strategy/docs/how-long-to-run-an-experiment (page dated 5 August 2026).
- Experiment memory: not documented publicly on the fetched pages. The 173K-experiment benchmark report is cross-customer research, not a per-account memory feature. Fetched: https://www.optimizely.com/field-notes/guides/127000-experiments/ (report dated 2026).
- Pre-launch power: frequentist mode "requires that you calculate the sample size before you start"; no in-product calculator is described on the fetched page.
- AI features: a results summary agent (the page calls it Mark's results summary) that explains each variation's impact and recommends next steps in plain language for completed A/B tests; follow-up questions in chat. Nothing on the page predicts before launch. Fetched: https://docs.optimizely.com/experimentation-strategy/docs/summarize-results (page dated 5 August 2026). Opal, the assistant, is described as an "experimentation co-pilot" that summarizes results, recommends next experiments from current results and drafts test plans with hypotheses, metrics and run-time estimates; no pre-launch outcome forecast is described. Fetched: https://www.optimizely.com/insights/blog/ai-and-feature-experimentation/ (post dated 11 February 2025).
- Export: `GET https://api.optimizely.com/v2/experiments/{experiment_id}/results` with `start_time`, `end_time`, `baseline_variation_id`; response includes `confidence_threshold`, `start_time`, `end_time`, `experiment_id`, `reach` (`total_count`, `baseline_count`, `treatment_count`, per-variation counts), `stats_config` (`confidence_level`, `difference_type`), and per-metric `name`, `aggregator`, `winning_direction`, a `results` map keyed by variation id (fields not expanded on the page), and `conclusion` with `winner` and `loser`. Fetched: https://docs.optimizely.com/feature-experimentation/api/get-experiment-results. The CSV export has 20 documented columns: Start Time (UTC), End Time (UTC), Variation Name, Variation ID, Is Baseline Variation, Metric Event Name, Metric Event ID, Metric Numerator Type, Metric Denominator Type, Metric Winning Direction, Numerator Value, Denominator Value, Metric Value, Improvement Status from Baseline, Improvement Value from Baseline, Statistical Significance, Is Improvement Significant, Confidence Interval - Low, Confidence Interval - High, Samples Remaining to Significance. Fetched: https://docs.optimizely.com/web-experimentation/docs/D9uo-reference-for-columns-in-csv-export-files-for-campaigns-and-experiments (page dated 20 July 2026).
- Gap: no pre-launch probability, no learned prior, no abstention. The results API is importable for exposures, dates and declared winners, and the CSV carries per-variation estimates with intervals and a significance flag.

### 1.3 Eppo (Eppo by Datadog since May 2025)

- Acquisition: Datadog announced the acquisition on 6 May 2025; the product continues as "Eppo by Datadog" inside Datadog Product Analytics. Fetched: https://www.datadoghq.com/blog/datadog-acquires-eppo.md (dated 6 May 2025).
- Statistics engine: fixed-sample frequentist, sequential (default), sequential hybrid, and Bayesian. CUPED uses a 30-day lookback on the same metric; CUPED++ adds all eligible pre-experiment metrics and assignment properties as covariates. Fetched: https://docs.geteppo.com/statistics/confidence-intervals/analysis-methods/ and https://docs.geteppo.com/statistics/cuped/ (pages show only a 2026 copyright).
- Historical priors: the Bayesian prior is set on the lift with mean zero and a spread described as "for 50% of experiments the lift will fall between -21% and +21%, and for 95% of experiments ... between -62% and +62%", described as typical across many kinds of experiment. The page warns intervals may be too narrow if your experiments usually show bigger lifts. No built-in fit to the account's own history. Fetched: https://docs.geteppo.com/statistics/confidence-intervals/analysis-methods/. A second statistics page states the prior as a normal distribution on the lift with mean zero and "a standard deviation of 0.05", adjustable in the Statistical Analysis Plan admin settings and "shared across all experiments using Bayesian analysis"; the two pages do not reconcile their spread figures, and neither fits the prior from the account's history. Fetched: https://docs.geteppo.com/statistics/confidence-intervals/statistical-nitty-gritty/.
- Experiment memory: a Knowledge Base of concluded, correctly configured experiments; each card shows name, dates, team, decision, primary metric impact, key takeaways, a variant image; search over names, hypotheses and takeaways; filters by outcome, decision, metric; sort by lift. No priors or predictions are described. Fetched: https://docs.geteppo.com/experiment-analysis/knowledge-base/.
- Pre-launch power: a Sample Size Calculator that "operates on top of your data" from an Entry Point SQL and outputs sample size and MDEs at different durations; past experiments are not mentioned. Fetched: https://docs.geteppo.com/statistics/sample-size-calculator/.
- AI features: not documented publicly on the fetched pages.
- Export: REST API at `https://eppo.cloud/api/v1` with an `X-Eppo-Token` header; the docs page gives `/api/v1/experiments` as the example and defers the schema to Swagger. Fetched: https://docs.geteppo.com/reference/api/. A third-party connector describes a "Get Experiment Results" action returning outcome, winning variant key, key takeaways and per-metric results. Fetched: https://pipedream.com/apps/eppo.md (secondary; field names not listed). Privacy: "Only data from the final stage of the pipeline (anonymized experiment aggregates) is egressed into Eppo's backend" and "Eppo doesn't export individual data from your warehouse." Fetched: https://docs.geteppo.com/data-management/data-pipeline/.
- Gap: the knowledge base is the strongest experiment memory among vendors but is descriptive. The Bayesian prior is a fixed industry-typical prior, not learned per account or per cell. No pre-launch probability or abstention.

### 1.4 LaunchDarkly Experimentation

- Statistics engine: Bayesian (threshold on probability to be best, credible intervals) and frequentist (significance level, multiple comparisons correction, sequential testing); CUPED covariate adjustment. Fetched: https://launchdarkly.com/docs/home/experimentation/results-data.md. The methodology guide states "Frequentist is the default approach in LaunchDarkly", that frequentist analysis defaults to sequential testing with a fixed-horizon t-test as the alternative, and that in Bayesian mode "By default, LaunchDarkly shrinks treatment results toward the control", with an uninformative-prior option so that results reflect only the collected data. Fetched: https://launchdarkly.com/docs/guides/statistical-methodology/choosing (no page date).
- Historical priors: the one current vendor with a learned prior (Qubit described a historical-experiment prior in its production engine in 2017, see 5.2). For numeric metrics the default "shrinkage prior" centers treatments on the control mean with variance w^2 = ybar0^2 gamma^2 + sigma0^2/N0, where gamma^2 is "the variance of observed relative differences across all experiments on the platform with the same metric type and aggregation function", stated as between 0.13 and 0.19; for binary metrics gamma^2 is about 0.04. The prior is platform-wide (pooled across all customers), not fitted to one account's ledger, and cannot be changed after the experiment starts. Fetched: https://launchdarkly.com/docs/guides/statistical-methodology/methodology-bayesian.
- Experiment memory: the results Summary stores hypothesis, key takeaways, shipped variation and reason for stopping per experiment; no cross-experiment search is described. Fetched: https://launchdarkly.com/docs/home/experimentation/results-data.md.
- Pre-launch power: a frequentist sample size calculator on the website and in-app; Bayesian experiments show an in-flight sample size estimator. Fetched: https://launchdarkly.com/docs/home/experimentation/results-data.md. The public calculator takes a minimum detectable effect, exposure rate, duration, control mean and standard deviation, significance level, allocation and power, in either direction (effect to sample size, or sample size to effect); it is frequentist in its terms and mentions no in-app counterpart. Fetched: https://launchdarkly.com/sample-size-calculator/ (no page date).
- AI features: not documented publicly for experiment prediction.
- Export: `GET /api/v2/projects/{projectKey}/environments/{environmentKey}/experiments/{experimentKey}/metrics/{metricKey}/results` returning type `ExperimentResults`. Fetched: https://github.com/launchdarkly/api-client-go/blob/v9.0.1/docs/ExperimentsBetaApi.md. That type carries `Metadata`, `Totals`, `Series`, `Stats`, `Granularity`, `MetricSeen`; the nested treatment-level fields were not fetched. Fetched: https://github.com/launchdarkly/api-client-go/blob/v9.0.1/docs/ExperimentResults.md. The Get experiment endpoint returns `winningTreatmentId` per iteration and `previousIterations` on expand. Fetched: https://launchdarkly.com/docs/api/experiments/get-experiment-results (served the Get experiment reference). The hosted MCP server's `get-experiment-metric-results` tool documents the per-treatment fields the REST reference leaves nested: `analyzedUnitCount`, `trafficCount`, `conversionCount`, observed mean and standard deviation, a relative-difference estimate with lower and upper bounds and a per-comparison `pValue`, plus `probabilityToBeBest`, `probabilityToBeatBaseline`, `expectedLoss` and `isSignificant`; it defaults to the current iteration and latest analysis. Fetched: https://mcp.launchdarkly.com/mcp/fm/install.
- Gap: the learned prior shrinks a running estimate toward control; it is not issued as a pre-launch forecast, is not per cell, and is not scored or gated.

### 1.5 Split (Harness Feature Management and Experimentation)

- Statistics engine: the rendered documentation pages returned HTTP 500 on six URL variants across both passes, so the engine was read from the documentation repository's source files. Frequentist methods only; a two-sided t-test ("Harness FME uses a two-sided test to detect differences between your baseline and your treatment in both directions"); sequential and fixed-horizon testing methods; significance is computed only once each treatment has "at least 355 independent observations", a rule of thumb attributed to a Microsoft paper, with floors of 10 for fixed horizon and 100 for sequential; significance and power thresholds are configurable, with 0.05 and 80% cited as common values rather than stated defaults; a multiple comparison corrections option; an experimental review period of 1, 7, 14 or 28 days with 14 recommended; an SRM guardrail that "detects uneven user allocation between treatment groups". No Bayesian mode and no priors. Fetched: https://raw.githubusercontent.com/harness/developer-hub/main/docs/feature-management-experimentation/statistical-approach.md, https://raw.githubusercontent.com/harness/developer-hub/main/docs/feature-management-experimentation/experimentation/key-concepts/statistical-significance.md and https://raw.githubusercontent.com/harness/developer-hub/main/docs/feature-management-experimentation/experimentation/setup/experiment-settings.md (source files carry no dates).
- Historical priors, experiment memory, AI features: not documented publicly on fetched pages.
- Export: the Share results download is fully documented. CSV has one row per metric with "Metric", "Impact", "Impact lies above", "Impact lies below", "Baseline metric value", "Comparison metric value", "pValue" (already corrected), "Baseline sample size", "Comparison sample size", "Sample Ratio", "Baseline treatment", "Comparison treatment", "Version start time", "Version end time", "Experiment significance threshold", "Minimum sample size", "Multiple comparison correction", "Metric aggregation". JSON adds `significanceThreshold`, `mcc`, `srmPValue`, `experimentalReviewPeriod`, per-metric `impact`, `impactLower`, `impactUpper`, `pValue`, `sampleSizeOfBaseline`, `sampleSizeOfComparison`, `mlde`, and a `metricDefinition` object recorded at download time. Fetched: https://developer.harness.io/feature-management-experimentation/use-fme/experimentation/experiment-results/sharing-experiment-results/index.
- Gap: the richest documented export of analysis settings alongside results, which is what a ledger importer needs; no prediction, memory or prior.

### 1.6 Amplitude Experiment

- Statistics engine: sequential testing, T-test, Bayesian and Thompson sampling options; CUPED (available on all plans; avoid for new-user targeting); Bonferroni correction. Fetched: https://amplitude.com/docs/feature-experiment/workflow/finalize-statistical-preferences (page dated 2026-10-21). Bayesian mode uses uninformative priors, Beta(1,1) for binary and an uninformative normal for continuous metrics, with a per-metric "Customize the Prior" toggle; Bayesian mode does not support CUPED; minimums of 25 conversions and 100 exposures per variant. Fetched: https://amplitude.com/docs/feature-experiment/experiment-theory/bayesian-statistics (page dated 2026-10-21).
- Historical priors: custom priors are typed by hand; past experiments are not mentioned.
- Experiment memory: not documented publicly.
- AI features: a Web Experimentation Agent announced on 17 February 2026 "Designs and launches experiments, analyzes results, and makes rollout or iteration decisions" with a human in the loop; an earlier agents post says the agent "designs targeted A/B tests to validate potential solutions, and requests your permission to run experiments". No pre-launch outcome prediction is claimed. Fetched: https://www.stocktitan.net/news/AMPL/amplitude-introduces-agentic-ai-analytics-for-the-next-era-of-2wdw7681w73x.html (syndicated copy of the press release; the investor-relations original returned 403) and https://amplitude.com/blog/ai-agents (post dated 10 June 2025).
- Pre-launch power: a proxy exposure event "uses historical data to estimate experiment duration" (same page). The Duration Estimator "pulls the last 29-30 days of traffic data from Analytics" (offset by one day), takes a baseline conversion metric or a manual rate, a default relative MDE of 5%, 90% confidence and 80% power, and returns an estimated duration with a scenario table; past experiments are not used. Fetched: https://amplitude.com/docs/feature-experiment/workflow/experiment-estimate-duration (page dated 2026-10-21).
- Export: no experiment results endpoint was found in two searches of the Amplitude docs; the Management API covers configuration and the Export API covers raw events. Not documented publicly.
- Gap: no pre-launch probability, no learned prior, no documented results export.

### 1.7 VWO (Wingify; VWO and AB Tasty combined under Everstone Capital, announced 20 January 2026)

- Corporate: Everstone is combining Wingify (VWO) with AB Tasty; the merged company reports 4,000+ customers and $100M+ annual revenue; Sparsh Gupta is CEO. Fetched: https://techcrunch.com/2026/01/20/everstone-combines-wingify-ab-tasty-for-100m-digital-experience-optimization-platform/ (dated 20 January 2026). VWO help pages now redirect to help.wingify.com.
- Statistics engine: SmartStats, a Bayesian engine that samples about 7 million draws, reports probability to beat baseline, probability to be best and "potential loss", and declares a winner at 95% chance to beat all with loss under a threshold; minimums of 25 conversions per variation, 1,500 visitors and one week. The prior is not described beyond "the conversion rate is considered to lie in the 0 to 100% range". The page says SmartStats applies to non-Data-Platform accounts. Fetched: https://help.wingify.com/hc/en-us/articles/59066062029977-How-Wingify-Calculates-a-Winning-Variation (page dated 24 September 2026).
- Historical priors: not documented publicly.
- Experiment memory: Learnings are free-text notes of up to 1,000 characters attached to a test, "up to 50 learnings to a test", and "Every learning point you add is automatically linked to the hypothesis being tested"; they are found by filtering the Hypotheses list by "With Learnings", and no keyword search over learnings is described. Fetched: https://help.wingify.com/hc/en-us/articles/59066074204825-Adding-Test-Learning-from-Wingify-Reports (page dated 24 September 2026; the former VWO URL redirects here). Hypotheses are "Wingify's central repository" under Plan, each created from an AI-generated idea and linkable to one test; the overview says the library "maintains a record of all tested ideas, their outcomes, and effectiveness" without naming the outcome fields. Fetched: https://help.wingify.com/hc/en-us/articles/58766164760345-Add-Ideas-to-Wingify-Hypotheses (page dated 12 August 2026).
- AI features: Copilot features are heatmap and session recording analysis, a visual editor from conversational commands, page selection and segment generation; upcoming items would "predict future user interactions", listed as planned, not released. Fetched: https://wingify.com/product-updates/vwo-copilot-ai-powered-optimization/ (dated 20 November 2024).
- Export: the REST campaign resource (page updated 28 April 2025) carries `status`, `thresholds.winningPercent`, `thresholds.losingPercent`, `thresholds.visitors`, `dataIntervalRange.startTime` and `endTime`, and per variation and goal `aggregated.visitorCount`, `conversionCount`, `conversionRate`, `standardError`, `revenuePerVisitor`, `revenuePerVisitorStandardError`, `isWinner` and `isLoser`, plus interval-wise counts; no explicit credible interval or probability field. Fetched: https://developers.wingify.com/v2/reference/campaign-resource-representation.
- Gap: Bayesian decision rules apply to running tests; memory is notes linked to hypotheses; nothing pre-launch.

### 1.8 Kameleoon

- Statistics engine: three approaches, fixed-sample frequentist, Bayesian and sequential, plus CUPED recommended with fixed sample sizes and said to work best when "you've run many experiments in Kameleoon" (as pre-experiment data, not as priors). Fetched: https://docs.kameleoon.com/user-manual/experiment-analytics/statistical-methods/choosing-the-right-statistical-method-for-ab-testing/. Bayesian mode "uses non-informative priors by default" and reports probability to beat the original and a credible interval on the improvement rate. Fetched: https://docs.kameleoon.com/user-manual/experiment-analytics/statistical-methods/bayesian. The "Statistics at Kameleoon" PDF returned 404 on three URLs in the first pass and on two further upload paths (help.kameleoon.com and docs.kameleoon.com) in the second; UNVERIFIED. A question page confirms the three approaches and warns that Bayesian analysis "can lead you in the wrong direction if the prior data is incorrect". Fetched: https://docs.kameleoon.com/user-manual/question/frequentist-or-bayesian-approach/.
- Historical priors: not documented publicly.
- Experiment memory: PBX 2.0 (changelog entry dated 11 June 2026) states that "Every experiment you've run is now automatically summarized in" a searchable knowledge base called Takeaways; an entry dated 9 October 2026 adds an AI-written description of what visitors saw; an entry dated 28 October 2026 adds MCP tools including `takeaway_list`, which recalls learnings from paused or stopped experiments. Fetched: https://docs.kameleoon.com/home/changelog.
- Pre-launch prediction: PBX Ideate (early access 20 February 2026, generally available 7 May 2026) analyses a page, proposes test ideas and ranks them "based on insights from more than 20,000 historical experiments", claiming to "achieve 63% accuracy on high-confidence predictions, 3x higher than the industry average of about 20%". The post gives no methodology, sample, definition of accuracy or confidence threshold, and no independent validation; it is the only vendor claim in this survey of a pre-launch prediction trained on an experiment archive. Fetched: https://www.kameleoon.com/blog/expanding-prompt-based-experimentation-with-pbx-ideate (post dated 7 May 2026) and the changelog above.
- AI features: AI Predictive Targeting "estimates each visitor's likelihood of converting for a specific goal" and buckets visitors into five Likelihood-to-convert segments (the Kameleoon Conversion Score); it needs 7 days of data and 100,000 visits on the goal, retrains every 10 minutes, is a Premium add-on, and predicts visitors, not experiment outcomes. Fetched: https://docs.kameleoon.com/user-manual/ai-predictive-targeting/overview.
- Export: `POST /experiments/{experimentId}/results` accepts `bayesian`, `sequentialTesting`, `enabledMultipleTesting`, `referenceVariationId`, `goalsIds`, `goalIdsCuped`, `dateIntervals`, `breakdown` and returns a `dataCode` to poll; result field names are on the poll endpoint. Fetched: https://docs.kameleoon.com/api-reference/experiment/request-experiments-results.md. The Get an experiment endpoint returns configuration and lifecycle fields (`id`, `name`, `hypothesis`, `status`, `dateCreated`, `dateStarted`, `dateEnded`, `dateCollectingDataStopped`, `goals`, `mainGoalId`, `variations`, `deviations`, `isMultipleTestingCorrection`) and no statistics. Fetched: https://docs.kameleoon.com/api-reference/experiment/get-an-experiment.md. The polled results object nests `variationData` by variation and goal with `visitCount`, `visitorCount`, `conversionCount`, `conversionRate`, `improvementRate`, `improvementRange` (`min`, `max`, `half`), `reliability` (the tutorial treats above 95% as a winner), `revenuePerVisitor`, `outlierBounds` and `cupedDataByGoalId`; no p-value or probability field is named. Fetched: https://docs.kameleoon.com/developer-docs/apis/automation-api-rest/tutorials/experiments/results-and-exports/retrieving-experiment-results-using-the-automation-api.md.
- Gap: Ideate is a ranked idea list with a self-reported accuracy and no published calibration, abstention or backtest; no outcome distribution or learned prior for a proposed experiment.

### 1.9 AB Tasty (Wingify group since January 2026)

- Statistics engine: Bayesian by default, beta-binomial with a "1+" style conjugate prior, one million samples, "chance to win" (Bonferroni-corrected across variations) and a 95% gain interval with median; Mann-Whitney U for transaction values; a recommendation to wait for at least 5,000 visitors per variation. Fetched: https://docs.abtasty.com/reporting-and-performances/reporting/understand-the-statistics-behind-your-reports/statistics-for-the-reporting.md. A frequentist mode can be enabled by the CSM; in it Reporting Copilot, Analysis Copilot and Opportunities views are unavailable. Fetched: https://docs.abtasty.com/reporting-and-performances/reporting/frequentist-analysis-mode.
- Historical priors: not documented publicly. The MDE calculator does retrieve precedents for sizing: it searches "all experiments which have been live over the past months" for one with "the exact same configuration" (targeting, URL sample and primary goal) and derives the detectable uplift from that data, falling back to an A/A test, another configuration or a manual calculator. Fetched: https://docs.abtasty.com/web-experimentation-and-personalization/campaign-creation-and-dashboard/how-to-use-mde-calculator.
- Experiment memory: Learnings (early adoption, enabled by the CSM): when a campaign reaches Analysis, Ended or Archived, one learning per campaign records an impact (Positive, Neutral, Negative, Unconclusive), a value tag (Surprising, Expected, Undefined, Biased, Push further, No impact) and up to 4,000 characters of feedback, stored in a Learning Library. Fetched: https://docs.abtasty.com/learnings/collect-learnings-from-your-experiments.

## 2. Open-source platforms and libraries

### 2.1 GrowthBook
- Statistics: Bayesian and frequentist engines; relative lift with delta-method variance; sequential testing by Asymptotic Confidence Sequences (inflates the standard error, not the mean); the Bayesian default is an improper flat prior, with a "proper prior" toggle whose default is N(0, 0.3^2) and, since GrowthBook 3.0, custom priors set on lift. The docs suggest basing a prior on past experiments' average lift and variance, by hand. Fetched: https://docs.growthbook.io/statistics/details.
- Experiment memory and meta-analysis: Insights offers a Dashboard (Scaled Impact with a positive-part James-Stein de-biasing once at least 6 experiments stopped; Win Percentage highlighted near 33% as an "ideal win rate"), Learnings (stopped experiments with won, lost or inconclusive decisions), Timeline, Metric Effects histograms "helpful if using informative priors", and Metric Correlations. No automatic prior or prediction. Fetched: https://docs.growthbook.io/insights. GrowthBook 4.0 (9 July 2025) describes Learnings as "a searchable knowledge base of all of your completed experiments"; GrowthBook 5.1 (22 September 2026) calls it "a living knowledge library" that an agent can seed by scanning past tests, alongside a hosted MCP server and contextual bandits. Fetched: https://dev.to/growthbook/growthbook-version-40-5d8a (GrowthBook's own post, republished) and https://www.growthbook.io/blog/growthbook-version-5-1. The Power Calculator takes a Fact Table, Segment or "Past Experiment" as its population to pre-fill weekly traffic and metric mean and variance; the effect size is typed by hand, with the guidance "Are there similar historical experiments, or pilot studies, and if so, what were their lifts?" Fetched: https://docs.growthbook.io/statistics/power.
- Export: `GET /experiments/{id}/results` returns `experiment` and `result` with `phase`, `dimension`, `results[]` carrying `totalUsers`, `checks.srm`, `metrics[]` with `metricId`, `variations[]` with `users` and `analyses[]` with `engine`, `numerator`, `denominator`, `mean`, `stddev`, `percentChange`, `effectStandardError`, `ciLow`, `ciHigh`, `pValue`, `risk`, `chanceToBeatControl`; result dates `dateStart`, `dateEnd`, `dateUpdated`; a bulk `/experiments/results` endpoint exists. Fetched: https://docs.growthbook.io/api/experiments/operation/getExperimentResults. A historical endpoint, `GET /api/v1/experiments/{id}/bulk-results`, "returns every successful snapshot for one experiment generated inside a date window", each item carrying `snapshotId`, `dateCreated`, the frozen analysis `settings` and per-dimension `results`; it is off by default behind `EXPERIMENT_BULK_RESULTS_ENABLED`. Fetched: https://raw.githubusercontent.com/growthbook/growthbook/main/docs/app/experiment-bulk-results-api.mdx.

## 3. Internal platforms described in public papers or blogs

### 3.1 Microsoft ExP
- The platform runs over ten thousand experiments a year with portal, execution, log processing and analysis services. Fetched: https://www.microsoft.com/en-us/research/publication/the-anatomy-of-a-large-scale-experimentation-platform/ (ICSA 2018).
- Prediction: "External Validity of Online Experiments: Can We Predict the Future?" analysed over a thousand experiments and millions of treatment-effect pairs: day-to-day z-scores have far heavier tails than Gaussian, the 14-day result fell outside the 7-day 95% CI 9% of the time (5% expected), standard errors increased 17% of the time going from 7 to 14 days, and novelty and primacy "are not the sole causes". Fetched: https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/external-validity-of-online-experiments-can-we-predict-the-future/ (dated 20 November 2024). This is the only vendor-or-platform source found that scores experiment-based predictions against later outcomes, and it predicts the same experiment's future, not a new experiment.
- Scale assessment: "Treatment Effect Assessment at Scale" evaluated 2,300 A/A scorecards and 44K A/B scorecards, found Fisher's method declared 22.0% of A/A scorecards significant, and adopted Benjamini-Hochberg; it argues "the quality of the metric set matters just as much as the choice of TEA methodology", a point about agentic systems lacking product context. Fetched: https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/treatment-effect-assessment-at-scale-accounting-for-correlated-metrics-and-metric-relevance-in-modern-experimentation/ (dated 15 July 2026). Article index fetched: https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/.
- Experiment memory: "Patterns of Trustworthy Experimentation: Post-Experiment Stage" (Machmouchi and Gupta, 24 December 2021) states that "Collecting the hypothesis, A/B test metadata, and metric movements observed provides a living history of feature ideas", that "We can perform meta-analysis to correlate the type of hypotheses with specific metric movements", and that "a library of hypotheses can also serve as an Experiment Corpus to properly evaluate and detect flaws in your metrics". Fetched: https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-post-experiment-stage/.

### 3.2 Netflix XP

### 3.4 Airbnb ERF
- YAML-declared experiments, nightly processing, p-value and delta sparklines, retired experiments keep their data "for future reference". ### 4.2 What the Spotify 2026 surrogacy work says about calibration
- Unadjusted gpt-4o-mini predictions "recovered only 39% of the observed human treatment effect" on Upworthy, a systematic shrinkage toward zero rather than noise. Calibration on human A/B data recovers the effect only if surrogacy (LLM output fully mediates the effect) and comparability (the LLM-to-human mapping is stable across experiments) hold; OLS failed the falsification test by 3.8 standard errors while tree ensembles passed; averaging several LLM draws per unit reduces attenuation; the assumptions "can never be proven for a treatment that has not been tested before" and weaken as treatments move away from past ones; model changes invalidate a calibration. Headline: "User experiments work by design, LLM-based experiments by assumption." Fetched: https://engineering.atspotify.com/2026/8/when-can-llms-replace-humans-in-a-b-tests/ (dated 13 August 2026).
- The follow-up paper, "When Can You Ship on Evals Alone? Trial-Level Surrogacy for Offline Evaluation of LLM Systems" (Schultzberg, submitted 7 October 2026), derives the ship, test or kill rule in the 4.1 table and finds on 183 Upworthy interventions that the pooled eval-to-outcome relationship is weak despite precise measurement on both sides, so the gate sends everything to a live test. Fetched: https://arxiv.org/abs/2610.10142. The May 2026 post that preceded both (3.8) places evals before the experiment as a funnel, not in place of it.
- Implication for a predictor ladder: an LLM or agent signal must be stacked at weight zero and earn weight out of sample against the ledger, and a novelty trigger must abstain where comparability cannot be argued.

### 4.4 Synthetic survey panels: fidelity evidence outside A/B testing
- Argyle, Busby, Fulda, Gubler, Rytting and Wingate, "Out of One, Many" (Political Analysis, 2023): GPT-3 conditioned on socio-demographic backstories from real survey participants produces "silicon samples" whose response distributions match those of human subgroups, a property the authors call "algorithmic fidelity"; the abstract reports no numeric correspondence. Fetched: https://arxiv.org/abs/2209.06899 (submitted 14 September 2022; DOI 10.1017/pan.2023.2).
- Bisbee, Clinton, Larson and co-authors, "Synthetic Replacements for Human Survey Data? The Perils of Large Language Models" (Political Analysis, 2024): ChatGPT personas scoring 11 groups on feeling thermometers reproduce ANES averages, but "there is less variation in responses than in the real surveys", "regression coefficients often differ significantly from equivalent estimates obtained using ANES data", distributions shift with minor prompt changes, and "the same prompt yields significantly different results over a 3-month period". Fetched: https://ai.updf.com/paper-detail/synthetic-replacements-for-human-survey-data-the-perils-of-large-bisbee-clinton-58d735a54d3aba79ad3bffbfa2433d8e5ee27313 (mirror of the abstract; the publisher page and PDF returned 403; DOI 10.1017/pan.2024.5).
- Kim and Cho, "Distributional Validity of a Korean Synthetic Persona Panel: Evidence From the Korea Media Panel Survey" (IEEE Access 14: 148208 to 148229, 2026): about 8,000 personas per model (Gemini 3.5 Flash and EXAONE) answering service-use and attitude items show mean absolute errors of 14 to 19 percentage points with item-mean correlations of 0.70 to 0.91; holdout calibration on 30% of the real data cut cell MAE from 18.3 and 15.1 to 4.9 and 4.4 points, yet direct estimation from that same subsample was more accurate at 3.6 points, and the correction did not transfer across waves; the authors call synthetic panels "not survey substitutes" and their value diagnostic. Fetched: https://arxiv.org/abs/2608.28615 (v2 dated 1 October 2026).
- Relevance: the pattern repeats the Spotify surrogacy result (4.2) in survey form. Synthetic responses match means, understate variance and need real data to calibrate, and once that real data exists it beats the calibrated panel; the Maiorano result in 4.1 adds that persona detail can lower validity. For a predictor ladder this is the case for a P0 and P1 built from the ledger before any agent signal, and for scoring the agent against held-out ledger rows rather than trusting a reported parity.

## 5. Research lines not already in related-work.md

### 5.1 Experiment prioritization and portfolio selection
- Liu and Chamberlain value an experimentation capability by the expected relative improvement from ranking propositions under reduced estimation error. Fetched: https://arxiv.org/abs/1909.03457 (September 2019; IEEE ICDM 2019).
- Dai et al. select which candidate models to A/B test using "a Bayesian surrogate model trained on historical logs" and sequential exploration. Fetched: https://arxiv.org/abs/2105.13420 (NeurIPS 2020).
- Microsoft ExP's external validity study shows that even the same experiment's effect drifts week to week, which bounds how sharp any pre-launch forecast can be. Fetched: see 3.1 (dated 20 November 2024).
- Portfolio allocation papers are RW 1.2, RW 4.1, RW 4.5, RW 4.6. No paper was found that ranks a backlog of proposed product experiments by predicted outcome and scores the ranking; two searches on value-of-information prioritization returned practitioner heuristics only. Published screening systems that rank candidates before a live test exist for ad allocation algorithms (Yelp, 3.15) and ad creatives (Meta, 3.7), and one vendor sells an archive-trained idea ranking (Kameleoon, 1.8); none scores a proposed product experiment's outcome.

### 5.2 Meta-analysis of experiment archives
- Miller and Hosanagar analysed 2,732 A/B tests from 252 e-commerce companies over three years: price promotions and category or listing page tests show the largest effects; promotion type interacts with funnel position. Fetched: https://mackinstitute.wharton.upenn.edu/2020/empirical-meta-analysis-e-commerce-a-b-testing-practices/ (dated 1 March 2020).
- Optimizely's benchmark covers 173K correctly configured experiments across 1,200+ companies from 2018 to 2026: "Sound experiments win 23 percentage points more often than poor ones (58% vs. 35%)", where a win is a primary metric moving the intended way at 90% significance; over 90% of experiments target five metrics. Fetched: https://www.optimizely.com/field-notes/guides/127000-experiments/ (2026).
- Browne and Swarbrick Jones, "What works in e-commerce - a meta-analysis of 6700 online experiments" (Qubit Digital Ltd, 22 June 2017; methodology assured by PricewaterhouseCoopers UK): over 6,700 experiments with revenue per visitor as a goal, run between 9 July 2014 and 30 April 2017, with roughly 2,600 of them classified into 29 treatment categories. Average uplift by category: scarcity +2.9%, social proof +2.3%, urgency +1.5%, abandonment recovery +1.1%, product recommendations +0.4%, colour 0.0%, buttons -0.2%, calls to action -0.3%; "90% of experiments have an effect of less than 1.2% on revenue"; the distribution of all tests "roughly resembles a normal distribution, but with shallow tails". Directly relevant here: "In production we impose a fairly informative prior on these uplift variables based on analysis of historical experiments, which means that the model is sceptical of large uplifts/downlifts on a test-by-test basis", an early vendor instance of a prior learned from an experiment archive (the meta-analysis itself used an uninformative prior). Fetched: https://gwern.net/doc/economics/advertising/2017-browne.pdf (mirror copy; the Qubit URL redirects to Coveo; text extracted locally).
- Ebbes, Ascarza and Netzer pool many marketing experiments in a hierarchical Bayesian model and find unobserved customer responsiveness explains about two-thirds of effect variation, far more than campaign design or timing. Fetched: https://ideas.repec.org/p/ebg/heccah/1610.html (HEC Research Paper 1610, 2026).
- Relevance: cross-company meta-analyses give a program-level base rate (P0) but pool across heterogeneous programs, which RW 1.9 identifies as a calibration failure mode.

### 5.3 Win-rate estimation
- Published program win rates found in this pass: Spotify about 12% (3.8); Optimizely 58% for well-set-up versus 35% for poorly set-up experiments at a 90% threshold (5.2); GrowthBook's guidance highlights 33% as an ideal (2.1); the RW 3.4 table (Microsoft 33%, Bing 15%, Booking, Google Ads and Netflix about 10%, Airbnb Search 8%). Definitions differ (shipped, significant positive at 90% or 95%, learning). A ledger format needs an explicit decision field and the threshold that defined it.

### 5.4 Predicting long-term effects from short-term
- Duan, Ba and Zhang (LinkedIn, WSDM 2021): surrogate-based tests have high false positive rates; adjustment and guidelines. Fetched: https://arxiv.org/abs/2106.01421.
- Zhang et al. (Netflix): 14-day auto-surrogate matches day-63 decisions about 95% of the time. Fetched: https://arxiv.org/abs/2311.11922.
- Sigerson, Cunningham, Chou et al. (25 authors from 15 platforms, August 2026): sign reversals are rare and cluster in content quality, hyper-monetization and pricing; a univariate auto-surrogate is hard to beat; "there is no substitute for a well-run long-term experiment". Fetched: https://arxiv.org/abs/2608.08043.
- PROXIMA (April 2026) audits whether a proxy leads to correct launch decisions with directional accuracy and segment fragility on 80 simulated tests built from Criteo and KuaiRec. Fetched: https://arxiv.org/abs/2604.14352.
- Hohnhold, O'Brien and Tang (Google, KDD 2015): an experimental methodology for measuring long-term user learning (ads blindness and sightedness) on Google Search ads, and a model that uses "metrics measurable in the short-term to predict the long-term" once users have adjusted; applied to an auction change that raised the weight of ad quality and to a 50% reduction in mobile ad load. Fetched: https://research.google/pubs/pub43887/ (listed there as "Focus on the Long-Term: It's better for Users and Business"). Surrogate index theory is RW 2.1.
- Relevance: these predict the long-run outcome of a running test; a pre-launch forecast is upstream and could be scored against either horizon.

### 5.5 Transfer and pooling across experiments and products
- Sales, Patikorn and Heffernan (EDM 2018): partial pooling across unrelated A/B tests on ASSISTments improves accuracy and reduces multiple-comparison problems at the cost of small bias. Fetched: https://par.nsf.gov/biblio/10095372.
- Ng and Imbens (January 2026): a Bayesian decision-theoretic framework where "hierarchical models use findings from past experiments as prior information on treatment effects", with losses defined by the experiment team, tested on real and simulated Amazon supply-chain experiments. Fetched: https://arxiv.org/abs/2601.20031.
- Mudd et al. (March 2026): Bayesian Hybrid Shrinkage with an experiment-specific local shrinkage factor to break the winner's curse, evaluated at Meta. Fetched: https://arxiv.org/abs/2603.12867.
- LaunchDarkly's platform-wide gamma^2 (1.4) is an industrial instance of pooling across customers; Qubit's 2017 production prior "based on analysis of historical experiments" (5.2) is an earlier one. Spotify's 2026 position (3.8) sets the practical bar for such priors: a corpus of more than about 200 representative experiments per program and a calibration check, since a poorly calibrated prior leaves the false positive rate unbounded. Local empirical Bayes is RW 7.1.
- Relevance: these shrink or decide after the data arrive. None issues the prior as a scored forecast before launch or gates its use by out-of-sample skill.

### 5.6 Sample-size planning informed by past experiments (assurance)
- O'Hagan, Stevens and Campbell define assurance as "the unconditional probability of a positive outcome", the prior expectation of power over a prior on the treatment effect. Fetched: https://tonyohagan.co.uk/academic/abs/assurance.html (Pharmaceutical Statistics 4:187-201, 2005).
- Pan and Banerjee unify Bayesian sample size determination with separate design and analysis priors. Fetched: https://arxiv.org/abs/2112.03509 (December 2021).
- Industrial calculators use historical metric variance (Statsig, Eppo, Confidence) and in Statsig's case a previous experiment's audience, but none uses a prior over the effect size fitted from the ledger; see 1.1, 1.3, 2.11.
- Relevance: assurance is the natural bridge between a P1 cell prior and a pre-launch power statement.

### 5.7 Benchmarks and datasets
- Criteo uplift benchmark: 13.9 million samples from randomized trials, about 210 times earlier datasets. Fetched: https://arxiv.org/abs/2111.10106 (November 2021).
- Hillstrom MineThatData e-mail dataset: 64,000 customers, three arms, visit, conversion and spend over two weeks; posted 20 March 2008; no license stated. Fetched: https://blog.minethatdata.com/2008/03/minethatdata-e-mail-analytics-and-data.html.
- UpliftBench (August 2026): 12 estimators across dataset families (IHDP, Jobs, ACIC, Revenue-Synthetic); Qini shows no detectable alignment with effect accuracy on IHDP. Fetched: https://arxiv.org/abs/2608.00915.
- Twin-2K-500 (4.1) for digital twins; PROXIMA's 80 simulated tests (5.4).
- Upworthy and ASOS are RW 6.1 and RW 6.4. No benchmark was found whose task is to forecast a single experiment's outcome before launch and score it.

Observations: decision-like fields are more common than the first pass found. Harness (`stateSummary`), GrowthBook (`status`), Statsig (Console API `launchedGroupID` and `decisionReason`), Optimizely (`Is Improvement Significant`, `conclusion.winner`), VWO (`isWinner`, `isLoser`), Mixpanel (Decide `success`), Dynamic Yield (`Declaration`) and LaunchDarkly (`winningTreatmentId`) each export one, but each means something different (a shipped group, a significance flag, a Bayesian threshold crossing or a typed-in boolean), which is why a ledger needs the decision rule and threshold as fields rather than a bare label. Only Statsig, Harness and Convert export the method or adjustment flags (CUPED, sequential, correction, `stats_methodology`) needed to interpret an interval, and only Convert exports power diagnostics; Statsig lacks a stable experiment id in the view; Optimizely's API and LaunchDarkly's REST reference hide the per-variation estimates in nested objects that only the CSV and the MCP tool spell out; Mixpanel's results cache is opaque. A reference ledger needs explicit fields for experiment id, variant, metric, estimate, variance or interval with its method, exposures, start and end, decision and decision threshold, plus provenance flags for variance reduction, sequential correction, multiple-comparison correction and winsorization.

### 7.2 Metric definitions
- Ratio metrics with a unit of analysis different from the unit of randomization need a delta-method variance (GrowthBook, Fetched: https://docs.growthbook.io/statistics/details; Adobe lift intervals, 1.10; Uber block bootstrap and delta method, 3.5). Importers should accept numerator and denominator (GrowthBook, Eppo caches "numerators and denominators" per 1.3) rather than a precomputed rate alone.
- Variance reduction changes what an interval means: Statsig warns to disable CUPED when comparing to external data (1.1); Confidence notes sequential intervals must use the CUPED-adjusted variance (2.11). The ledger must record whether the stored estimate is adjusted.
- Winsorization and outlier handling are applied silently by some vendors (Statsig, 1.1) and should be recorded.
- Enrollment-relative windows (Jetstream day 0, week 0, days28) versus calendar windows (most vendors) must both be representable.

### 7.3 Privacy expectations
- Warehouse-native vendors promise that only aggregates leave the warehouse: "Eppo doesn't export individual data from your warehouse" (1.3); Confidence "never stores raw user-level data" (2.11); Statsig retains exposures and raw user-level metrics for 90 days after conclusion (1.1). A ledger that stores only per-variant aggregates with counts matches the privacy posture organizations already accept, and must not require unit-level rows.
- Microsoft ExP published on adapting experimentation to EU data boundaries (article index, 3.1), so regional residency of the ledger matters for European programs.

### 7.4 Integration points
- SDK events: OpenFeature is the vendor-neutral evaluation API (CNCF incubating) and does not define results export (2.13); Confidence and Flagsmith rely on it or on their own SDKs. A ledger importer should not depend on SDK events; results arrive from warehouse tables, vendor APIs or CSV.
- Warehouse tables: Statsig view, Eppo aggregates, GrowthBook snapshots, Jetstream BigQuery tables, Harness Warehouse Native, Flagsmith ClickHouse or Databricks. SQL readers for these schemas cover most of the installed base.
- APIs: Optimizely, GrowthBook, LaunchDarkly, Kameleoon, Eppo, Convert and VWO document results endpoints; Mixpanel exposes an opaque results cache plus a decision endpoint; Adobe's Admin API lists Reports without documenting fields (1.10); Amplitude documents none.
- Files: Harness CSV and JSON, Statsig CSV, Optimizely CSV (20 columns), Adobe raw CSV, Dynamic Yield history CSV and daily Parquet.

### 7.5 Governance: audit and versioning
- Analysis settings are frozen at start in several products: Statsig locks the analysis type (1.1); LaunchDarkly locks the prior (1.4); Harness records statistical settings and metric definitions "at download time" in the JSON (1.5); GrowthBook snapshots carry `dateUpdated` and `phase`, with a separate historical bulk-results endpoint (2.1); Eppo keeps activity logs of flag changes and who ran queries (1.3); OSF registrations are frozen and time-stamped with an embargo option (2.13); GrowthBook's bulk-results endpoint returns every historical snapshot with the settings frozen at analysis time (2.1); Statsig's Console API stores `decisionTime` and `decisionReason` with the experiment (1.1).
- A forecast card should follow the same pattern: frozen at issue time with the ledger snapshot id, scored only against results admitted later, and versioned so a rolling-origin backtest can be reproduced.

### 7.6 What a one-day pilot needs
1. One importer for the organization's current export (Statsig view, Harness JSON, GrowthBook API, or a CSV mapped to the ledger fields in 7.1), with provenance flags.
2. A decision field and threshold for each concluded experiment, since the vendors that export one define it differently and several export none (7.1).
3. At least one cell with enough concluded experiments to fit a P1 prior; GrowthBook's own Scaled Impact de-biasing requires at least 6 stopped experiments (2.1), and the Microsoft drift results (3.1) argue for conservative intervals on small cells.
4. A rolling-origin backtest over the imported history that reports log score, Brier skill against the P0 base rate, coverage and the abstention rate, before any forecast is shown for a live proposal.
5. Aggregates only, no unit-level data, to match the privacy posture in 7.3.
6. An optional agent adapter registered at weight zero, so the pilot can report whether an LLM or simulation signal earns weight on this ledger, as the Spotify surrogacy results suggest it often will not (4.2).
